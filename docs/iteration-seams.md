# Iteration Seams

Where to plug in changes when the design language or tech stack shifts.
Components are **forbidden** from baking in design choices outside these
seams; if you find a hard-coded color in `components/cinema/*.tsx`, that
is a bug.

## 1. Visual / design language

### Single swap point: `lib/cinema/theme.ts`

Every visual decision lives here:

| Token group         | Affects                                              |
| ------------------- | ---------------------------------------------------- |
| World materials     | Sand-table base, building tops/sides, streets, lines |
| Atmosphere          | Background, fog near/far, fog color                  |
| Light               | Ambient + key (intensity, azimuth, elevation, color) |
| postFx              | tilt-shift, grain, vignette intensities              |
| Accent / signal     | Hyperlocal pulse (cyan), mirror reversal (magenta)   |
| Scene framing       | World extent, default building height, scale         |

To re-skin the entire site, edit `sswtCinemaTheme` and rebuild. No component
changes needed.

### Per-act / per-beat theme override

`resolveTheme(overrides?)` returns a merged theme. Future use: drive the
mirror beat (Act 3.2) to a deep-purple variant by passing an override at
that beat's range.

## 2. Camera engine

### Single swap point: `components/cinema/CameraRig.tsx`

CameraRig consumes `CameraScore` (data) + `t` (number). It outputs an
imperative camera transform.

Today: hand-rolled interpolation in `lib/cinema/cameraInterp.ts` + spring
smoothing in `lib/cinema/spring.ts`.

Tomorrow swappable to:

- **Theatre.js** — replace CameraRig with a Theatre studio-driven sequence;
  CameraScore becomes a Theatre object exporter
- **Framer Motion 3D** — replace with `motion.group` and motion values
- **GSAP timeline** — replace internal interpolation with a GSAP timeline
  that reads the same score data

The score data shape (`lib/cinema/types.ts`) is the contract; everything
else is a renderer.

## 3. Render layer

### Single swap point: `components/cinema/CinemaCanvas.tsx`

CinemaCanvas mounts a render pipeline. Today: R3F (`@react-three/fiber`) +
SandTable + CameraRig + Atmosphere.

Swappable to:

- **Vanilla three.js** with imperative scene setup
- **PIXI.js** for a 2D-only stylized version
- **CSS / SVG** for a non-WebGL path (already exists at `/storyboard`)
- **A different sand-table renderer** (e.g., voxel, holographic, isometric
  pixel) — keep `<CinemaCanvas>` as the slot; replace its children

Score data, theme, frontmatter all stay the same; only the children change.

## 4. Geometry pipeline

### Source of truth: `public/case-studies/sswt/map-geometry.json`

Generated by `scripts/export-sswt-assets.ts` from the source research repo.
The portfolio site treats this as a static input.

To swap to a different city / different scale model:

1. Re-run `pnpm export:sswt` against another source dataset, OR
2. Author a new asset folder under `public/case-studies/<slug>/` and a
   matching loader in `lib/content/`.

Sand-table renderer reads through the loader, so geometry source is
swappable without touching components.

## 5. Content / authoring

### Single swap point: frontmatter in `content/case-studies/<slug>.mdx`

Authors write MDX with `acts: Act[]`. Each beat declares the five-tuple
(claim · shotRef · hud · fallbackFigure · sources). `pnpm content:lint`
enforces the contract.

To swap to a different content backend (CMS, headless, database):

- Replace `lib/content/load-case-study.ts` with a fetcher that returns the
  same `LoadedCaseStudy` shape
- Frontmatter Zod schema becomes the API contract for the CMS

## 6. Animation timing / progress

### Single swap point: `lib/cinema/scrollCinema.ts`

`scrollToT(scrollProgress)` is the **only** place where DOM scroll becomes
cinema time. No component reads scroll directly.

To swap from scroll-driven to:

- **Autoplay**: replace with a setInterval / rAF that advances t
- **Click-to-advance**: replace with discrete state machine
- **Scrubber UI**: expose t as a controlled value
- **Theatre.js**: hand t over to Theatre's playback head

…edit one function and the whole cinema reacts.

## 7. HUD layer

### Single swap point: `components/hud/HudLayer.tsx` + `Hud` discriminated union

HUD kinds are an enum in `lib/cinema/types.ts`. Adding a new kind:

1. Extend the `Hud` union with a new variant
2. Update Zod schema in `lib/content/case-study-schema.ts`
3. Add a render branch in `HudLayer.tsx`

The cinema canvas, score, and theme are untouched.

## 8. Post-processing slots (currently empty)

Theme reserves four post-fx tokens (tilt-shift, grain, vignette). The
intended add-point is a `<PostFxStack>` component that mounts inside the
R3F canvas after the scene meshes. Until shaders are written, the tokens
are inert; once the shader passes land, the existing token values flow
through unchanged.

## 9. New tech stack additions — checklist

When considering a new dependency:

- [ ] Does it touch one of the seams above? (good — bound to one swap point)
- [ ] Is it a content-shape change? (update Zod schema first, components after)
- [ ] Is it a new render target? (replace CinemaCanvas children only)
- [ ] Is it a new animation engine? (replace CameraRig only)
- [ ] Is it none of these but spans multiple? (re-think — likely too coupled)

If a new dep wants to dictate behavior across multiple seams, treat it as
a re-architecture conversation, not a drop-in.
